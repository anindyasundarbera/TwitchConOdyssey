# Twitch and AWS platform findings

**Retrieved:** 2026-11-01. **Scope:** official Twitch and AWS docs on input, identity, delivery, Extensions, latency, and IVS. This is not evidence of a working integration or sponsorship. **Confidence:** high on documented behavior and limits; medium on demo feasibility because no account or integration was inspected.

## Decisive findings

- **Chat input is available through EventSub.** `channel.chat.message` delivers messages and identifies the channel and chatter. It requires `user:read:chat`; with an app token, also `user:bot` from the chatting user and `channel:bot` from the broadcaster or moderator status. Twitch documents WebSocket and webhook transports; its chat setup guidance points to WebSockets for user-hosted clients and webhooks for cloud-hosted bots. These are authorization and transport requirements, not a latency SLA. [EventSub subscription types](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types), [chat authentication](https://dev.twitch.tv/docs/chat/authenticating)
- **Treat delivery as at-least-once and potentially interrupted.** EventSub may redeliver an event with the same envelope `message_id`; deduplicate it before processing. Also retain the chat event’s own message ID as an input idempotency key. On a lost WebSocket, Twitch does not replay missed events after reconnect, so expose degraded input state and fail closed for the current turn instead of silently assuming a complete vote. [EventSub duplicate handling](https://dev.twitch.tv/docs/eventsub), [WebSocket handling and recovery](https://dev.twitch.tv/docs/eventsub/handling-websocket-events)
- **Extension buttons are an interface, not turn logic.** An Extension is a sandboxed webpage with a Twitch helper and PubSub messaging. `send()` is topic-permissioned; its reference specifically describes broadcaster channel/whisper sends. Treat viewer clicks as untrusted input to an authenticated game endpoint: validate the Extension JWT and never let client state apply actions. Twitch’s PubSub API limit is **100 outbound messages/minute per Extension client ID and broadcaster**; this is not an input-vote limit. [Extensions overview](https://dev.twitch.tv/docs/extensions), [Extensions reference](https://dev.twitch.tv/docs/extensions/reference), [Twitch API: Send Extension PubSub Message](https://dev.twitch.tv/docs/api/reference)
- **Identity can support a viewer cap, with an anonymous caveat.** Extensions expose opaque IDs: logged-in `U-` IDs are stable across sessions/channels without revealing the account; anonymous `A-` IDs are transient and must not back persistent records. Optional identity linking reveals the Twitch ID after consent. One influence per turn is implementable for stable chat IDs or Extension `U-`/linked identities, but is not a person-level cap for `A-` sessions. [Extensions identity and JWT reference](https://dev.twitch.tv/docs/extensions/reference)
- **Extension release is not a safe public-demo assumption.** Local/Hosted Test are restricted to configured test accounts and a small set of Twitch staff. Twitch currently estimates **8–14 days** for review. Private testing is plausible; broad viewer access depends on approval and timing. [Extension lifecycle](https://dev.twitch.tv/docs/extensions/life-cycle)
- **Do not promise Twitch end-to-end 3–5 second sync.** Twitch has broadcaster-selectable Normal/Low Latency modes but no universal end-to-end figure. Delay varies by player, network, and optional stream delay. Use server receipt time and a hard cutoff; reject late input or assign it to the next turn. Measure the actual demo path. [Twitch Low Latency Video](https://help.twitch.tv/s/article/low-latency-video), [Twitch stream delay](https://help.twitch.tv/s/article/how-to-add-stream-delay)
- **IVS has separate streaming products and a narrow optional fit.** AWS says IVS Low-Latency channels can deliver under 5 seconds and Real-Time stages under 300 ms; a stage rebroadcast to a channel has channel latency. These IVS figures do not establish Twitch latency or prove a Twitch stream uses IVS. IVS timed metadata can anchor stats or quiz cues to playback, though insertion is not guaranteed to be immediate. It helps only if the project controls an IVS broadcast/player path. [IVS Low-Latency overview](https://docs.aws.amazon.com/ivs/latest/LowLatencyUserGuide/), [IVS timed metadata](https://docs.aws.amazon.com/ivs/latest/LowLatencyUserGuide/metadata.html), [IVS Real-Time overview](https://docs.aws.amazon.com/ivs/latest/RealTimeUserGuide/)

## Mapping to the game concepts

| Concept | Provider capability | Game-owned obligation / boundary |
| --- | --- | --- |
| 20-second planning, 5-second locked resolution | EventSub chat; Extension choices via an authenticated service path. | The game owns phase checks, receipt time, cutoff, parsing, validation, and replay-safe resolution. Twitch does not guarantee delivery inside a turn. |
| One viewer influence; K rival cohorts | Chat sender IDs; Extension opaque or consent-linked identity. | Deduplicate, then enforce one slot per eligible identity per turn. Cohorts, weights, bot backfill, and fairness are game rules, not Twitch features. |
| Moderation Forcefield | EventSub can report chat and selected moderation-related events. | Convert only to a fictional, non-punitive game effect such as Hype; never ban, time out, or otherwise punish a real chatter as part of the mechanic. Twitch does not supply a “spam becomes Hype” feature. |
| AWS ScaleBoost | IVS transports/synchronizes video and timed metadata. | A “congestion becomes a speed lane” effect is fictional game logic; IVS docs do not say IVS detects game congestion or changes game speed. Treat IVS metadata as an optional playback cue if an IVS media path exists. AWS/IVS documentation establishes capability, not event sponsorship or a Twitch integration. |

**Brand boundary:** Keep Twitch Extension UI distinct from the separately broadcast game. Extension policy has its own restrictions on sponsorship content; that does not establish brand permission for in-game content. See [BRANDING.md](BRANDING.md) for the policy finding; obtain explicit rights evidence before making sponsorship or partnership claims.

## Unknowns / blockers

- No OAuth grants, Extension/EBS, channel, or latency measurement was verified. Consent, token custody, reconnects, throughput, and mobile/browser behavior remain untested.
- Public Extension deployment timing is uncertain until review status and queue time are known; testing-mode visibility is restricted. This can block a public-viewer Extension demo but not a test-account prototype.
- No AWS sponsorship, Twitch/AWS project arrangement, Amazon IVS channel/player, or cost/region fit is established. An IVS experiment is optional and should not displace the Twitch-first input design absent an explicit need to control the video path.
- No source guarantees full input-to-visible-action latency. Measure chat/Extension-to-engine and engine-to-viewer separately; do not apply IVS figures to Twitch playback.
