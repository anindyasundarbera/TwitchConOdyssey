## Required design outcome

### 1. Immersive launch and fullscreen

- Fill `100dvw × 100dvh` on load with no page scrolling or unrelated page
  chrome surrounding the game.
- Do not falsely claim that a web page can enter true fullscreen without user
  activation. The primary “Start Odyssey” action must request fullscreen.
- If fullscreen is denied or unavailable, remain in a polished edge-to-edge
  fallback.
- Handle fullscreen entry, denial, exit/Escape, resize, orientation, mobile safe
  areas, focus loss, and restoration safely.
- Preserve authoritative state across presentation-only viewport changes.

### 2. Everything necessary inside the game

- Put start, pause, resume, restart/new match, controls, sound, accessibility,
  fullscreen, Twitch mode/status, objective, and help inside in-game overlays or
  menus.
- Remove dependence on explanatory content outside the game viewport.
- Include coherent loading, ready, active, paused, disconnected, error,
  completion, deadline/failure, and restart states.
- Modal overlays must trap focus appropriately, be dismissible as intended, and
  never mutate authoritative state accidentally.

### 3. Game-like San Diego world

- Replace utilitarian map/navigation styling with a stylized San Diego
  arcade/runner presentation.
- Preserve approved route progression and named destinations, but express them
  diegetically rather than as a conventional navigation map.
- Establish readable background, midground, playfield, destination, hazard,
  character, effects, and HUD layers.
- Use depth, lighting, palette, landmarks, motion, iconography, and feedback
  deliberately without obscuring play.
- Avoid generic dashboards, dense card grids, map pins, route-planner controls,
  and data-heavy application aesthetics.
- Respect reduced-motion preferences and provide static equivalents for
  essential feedback.

### 4. Player-character presentation

- Give the character a distinctive, readable silhouette and orientation.
- Provide visible lane-change, forward-motion, collision/slowdown, recovery,
  delivery-success, and deadline/failure feedback.
- Keep decorative animation separate from authoritative position and collision
  values.
- Maintain character readability at desktop and mobile dimensions and against
  every world layer.
- Reuse suitable existing assets; do not introduce licensing ambiguity.

### 5. HUD and feedback hierarchy

- One clear progress indicator.
- Hazard/counter timer and phase state.
- One plain-language action/consequence preview.
- Current objective and next delivery destination.
- Fictional Hype pool/settlement state with no implication of real currency.
- Honest Twitch mode: live, disconnected, or fixture.
- Immediate input, lane-change, hazard, counter, collision, reward, delivery,
  and failure feedback.
- No high-speed raw-chat reading requirement.
- No essential information conveyed only by color, animation, hover, or sound.

### 6. Controls

- Preserve approved auto-forward, three discrete lanes, keyboard arrows, and
  gamepad D-pad behavior.
- Show contextual control prompts and input ownership/focus.
- Prevent browser scrolling or default key behavior while the game owns input.
- Support touch controls only if they can be integrated safely with current
  mechanics and verified within the deadline.
- Implement remapping only if the existing input architecture supports it
  without destabilizing authoritative behavior.
- Pause/settings/help input must not leak into gameplay commands.
- Same-tick and cutoff semantics remain owned by the deterministic engine.

### 7. Responsive and accessible presentation

- Verify at minimum `1440×1100` desktop and `390×844` mobile.
- Avoid clipped essential controls, accidental scrollbars, obscured playfields,
  unreadable overlays, unsafe-area collisions, and inaccessible modal states.
- Provide keyboard navigation, visible focus, semantic controls, useful labels,
  sufficient contrast, reduced motion, and non-color-only state communication.
- Maintain usable touch target sizes when touch controls exist.
- Preserve legibility under reasonable text scaling and browser zoom.

### 8. Performance and resilience

- Avoid unnecessary framework or dependency additions.
- Avoid layout thrashing, unbounded DOM growth, unbounded animation work, and
  effects that interfere with the deterministic tick path.
- Gracefully handle service disconnects, fixture mode, missing optional assets,
  fullscreen rejection, resize, and repeated pause/resume.
- Prefer CSS/compositor-friendly presentation and bounded effects.
- Record observed performance checks and limitations; do not invent FPS claims.
